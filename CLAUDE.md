# CLAUDE.md

Working rules for this repository. How to build, test, fuzz and benchmark is in
[Development.md](Development.md); this file is about how changes are expected to be made.

## What the project is

fastgpx is a C++23 GPX parser and polyline codec with a nanobind Python module. Speed is the
reason it exists, so a correctness fix that costs measurable parse or encode time needs a
justification in the commit message.

## Changing the parsers or the encoder

- Benchmark before and after against the previous commit using the Catch2 `[!benchmark]` cases
  (`fastgpx_test "[!benchmark][datetime]"`, `"[!benchmark][polyline]"`). Run each side several
  times; single runs on this project have been noisy by 2x. Put the numbers in the commit message.
- Verify on both toolchains: the MSVC build and the sanitized Clang build with
  `FASTGPX_BUILD_FUZZERS=ON`. Run the Catch2 suite, the `fuzz_<target>_corpus` replays, and a
  short fuzz run of the affected target before calling a change done.
- Undefined behaviour is a bug even when the current output looks fine. Validate before casts
  and arithmetic that can overflow; do not rely on the platform's behaviour.
- When the fuzzer finds a crash: minimise the input, fix the cause, add the input to
  `src/cpp/fuzz/corpus/<target>/` as a regression seed, and reference the issue in the commit.
  Do not weaken a fuzz target to get past a bug; if it must be masked temporarily, say so in the
  target's header comment and in the issue.

## Errors

- C++: throw a subclass of `fastgpx_error` from `fastgpx/errors.hpp`. `parse_error` for
  malformed data, `value_error` for values a function cannot operate on, `file_error` for I/O.
- Python: the hierarchy surfaces as `fastgpx.Error` (a `ValueError`) with `fastgpx.ParseError`
  beneath it; file failures are `FileNotFoundError`/`OSError`. New error paths follow this, and
  Python tests assert the specific type.

## Repository conventions

- Do not commit until the user explicitly says so; "LGTM" counts as clearance to commit the work it
  refers to. Preparing the commit message ahead of time is fine.
- Commit messages end with `Fixes #N` when they resolve an issue; merges to `main` close them.
- Issue labels: `fuzzer` only for findings from running the fuzzer or genuine undefined
  behaviour; `code-analysis` for things found by reading code.
- `src/fastgpx/*.pyi` are generated by nanobind at build time. Commit them only when the
  bindings changed, and call out any unrelated stubgen drift in the commit message.
- Sphinx builds with warnings as errors in CI. A new docstring or `.rst` change must build clean
  with `SPHINXOPTS=-W --keep-going`.
- `benchmarks/` scripts are imported by `tests/test_benchmarks.py`; keep their work under
  `if __name__ == '__main__':`.
